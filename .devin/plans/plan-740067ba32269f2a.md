# Card-Based Combat Integration with QTE System

Plan to integrate the card combat addon with the 3D turn-based battle template, replacing traditional Attack/Skills/Defend with a card-based system similar to Slay the Spire, enhanced with QTEs for attack execution similar to Expedition 33. Uses action points for card costs, reactive QTEs for dodge/parry, keeps Items/Run as separate buttons, and enemies retain their AI-based attack system.

## Current System Analysis

### Existing Battle System (`battle-manager/`)
- **BattleManager.gd**: Main turn-based combat controller with attack/skill/defend/item/run actions
- **BattleHud.gd**: UI with action buttons (Attack, Skills, Defend, Items, Run)
- **Battler.gd**: Character stats, targeting, movement, combat actions
- **Skills**: Resource-based skill system with effects
- **Items**: Inventory and item usage system

### Card Combat Addon (`addons/card_combat/`)
- **CardData**: Card resources with costs, effects, spell effects
- **CombatSession**: Card-based combat orchestrator
- **CombatDeck**: Hand, draw pile, board, graveyard management
- **CombatConfig**: Balance parameters
- **SpellEffect**: Modular effect system

### QTE Addon (`addons/QuickTimeEvent/`)
- **QTE**: Abstract base class for QTEs
- **CountdownQTE**: Specific timed input QTE
- **Modular and extensible**

## Implementation Plan

### Phase 1: Remove Traditional Combat Actions
1. **Remove Attack/Skills/Defend buttons from BattleHud**
   - Keep Items and Run buttons (per user preference)
   - Remove `_on_attack_pressed()`, `_on_skills_pressed()`, `_on_defend_pressed()`
   - Remove skill selection container (will be replaced by card UI)
   - Keep item selection container (Items remain as buttons)

2. **Remove combat action logic from BattleManager**
   - Remove `queued_action`, `queued_skill`, `queued_item` variables
   - Remove `_on_action_selected()` handling for attack/skill/defend
   - Keep item and run handling
   - Remove skill targeting logic (will be replaced by card targeting)

3. **Remove skill-based combat from Battler**
   - Keep stats, health, movement, targeting system
   - Remove `use_skill()` method
   - Remove `default_attack` and skill list
   - Keep `take_damage()`, `take_healing()`, `defend()` (may be repurposed)

### Phase 2: Integrate Card Combat System
1. **Create CardBattleManager**
   - Bridge between 3D battle system and card combat engine
   - Manages CombatSession for card-based combat
   - Handles card play, mana, deck management
   - Integrates with existing Battler stats and 3D positioning

2. **Create CardUI system**
   - Replace skill selection with card hand display
   - Card play interface with drag/click functionality
   - Card targeting UI (reuse existing targeting highlights)
   - Action points display (AP system for card costs)

3. **Integrate CombatSession with 3D battlers**
   - Map CombatSession side 0 to player, side 1 not used (enemies keep AI)
   - Convert card effects to 3D battler actions
   - Use existing Battler stats for card calculations
   - Preserve 3D movement and animations for card actions
   - Enemies continue using existing AI skill system

### Phase 3: Add QTE System Integration
1. **Create QTEManager**
   - Manages QTE triggering during card execution
   - Configurable QTE types per card/attack
   - Success/failure handling with damage modifiers
   - Reactive QTEs for dodge/parry when player is attacked

2. **Create QTE configuration system**
   - Resource-based QTE definitions (difficulty, type, timing)
   - Card metadata to specify QTE requirements for attacks
   - Enemy attack metadata to specify dodge/parry QTE opportunities
   - Modular QTE types (timed, sequence, mash, etc.)

3. **Integrate QTEs into card execution**
   - When player ends turn, execute queued card actions with QTEs
   - QTE success = damage boost / bonus effect
   - QTE failure = reduced damage / normal effect
   - When enemies attack player, trigger reactive dodge/parry QTEs
   - Successful dodge/parry QTE = avoid/reduce damage

### Phase 4: Resource-Driven Configuration
1. **Create CardBattleConfig resource**
   - Balance parameters for card combat
   - AP system settings (AP per turn, max AP, AP regeneration)
   - QTE difficulty settings
   - Integration settings with 3D system

2. **Create Card resources for game**
   - Attack cards with QTE requirements
   - Skill cards with effects
   - Defense/dodge cards
   - Resource-based card definitions

### Phase 5: System Architecture
1. **Modular component design**
   - CardBattleManager (independent of 3D specifics)
   - QTEManager (independent of combat system)
   - CardUI (independent of battle logic)
   - Clear interfaces between components

2. **Event-driven communication**
   - Signals for card played, QTE completed, turn ended
   - Decoupled components for easy modification
   - Extensible for new card types and QTE types

## Risks/Considerations

### Integration Complexity
- Card combat engine was designed for 2D board games, needs adaptation for 3D battler system
- Need to map card effects to 3D animations and movements
- Targeting system may need adjustments for card-based targeting
- Reactive QTEs for dodge/parry require timing integration with enemy attack animations

### Performance
- QTE system slows down game time (Engine.time_scale), need to ensure this doesn't break 3D animations
- Card UI rendering overhead in 3D scene

### Backwards Compatibility
- Removing existing combat actions breaks current battle system
- Need to ensure this is a complete replacement, not hybrid
- Consider creating backup of original system

### Extensibility
- Design should allow adding new card types easily
- QTE system should support new QTE types beyond CountdownQTE
- Resource-driven configuration for easy balance adjustments

### Scope
- This is a significant architectural change
- Need to carefully plan the order of implementation
- Consider iterative approach: first integrate cards, then add QTEs
